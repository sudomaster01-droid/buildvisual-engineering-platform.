Executive Summary
AGREED PRODUCT DECISION
BuildVisual is a single-engineer web workspace that turns a drawing, voice description or short written
house requirement into a cinematic architectural walkthrough that can be reviewed, corrected,
downloaded and shared.
Product promise
The engineer provides the house intent; the platform performs interpretation, model construction, automatic
design completion, camera planning, AI video generation, clip assembly and delivery. The engineer does not
compose video prompts or choose every finish and camera setting.
Chosen hybrid
The selected approach combines a model-first workflow inspired by Japanese BIM practice, geometry-led
visualization associated with US architectural workflows, and the speed and motion of generative video associated
in the conversation with Chinese tools. The platform generates prompts internally and supplies model-derived
reference images to the video provider.
Truth boundary
 - This is an architecture plan, not proof that any provider can hard-lock architectural geometry.
 - A few-minute delivery and the previously discussed USD 3-12 per-video estimate are targets only until benchmarked.
 - The first implementation milestone is an end-to-end production slice that creates and rectifies a real video.
 
Decision labels
AGREED means directly chosen in the conversation. PROPOSED means a concrete implementation
recommendation. VERIFY marks a provider capability, cost, quality or timing claim that still needs evidence. Use
these labels as a guard against turning a design target into a promise.
Detailed execution plan
Translate the design into a small vertical slice: one supported source input, one interpretation path, one
model/reference path, one provider adapter, one assembly path and one quality check. Build around actual
artifacts and state transitions instead of mocking away the difficult integration. After this slice succeeds, expand
input coverage and add more robust rectification and operations.
Evidence and ownership
For every open decision, record the owner, the evidence required, the test input, the acceptance threshold and the
date the decision is reviewed. Keep failed examples in the evaluation set. A good result that cannot be reproduced
or traced to a specific configuration is not enough to establish reliability.
Failure and acceptance checks
 - Run automated and manual tests with both successful and failed jobs.
 - Record cost, end-to-end time, QA outcome and correction success on each test.
 - Release only when the agreed user journey works and the remaining limitations are documented.

User Problem and Desired Outcome
AGREED PRODUCT DECISION
The site must make it easy for an engineer to help a client understand a proposed home. Its value is
the finished visual explanation, not the complexity of the technology behind it.
Problem statement
Drawings and plans are difficult for many clients to imagine in three dimensions. Misunderstanding can create
anxiety, repeated explanations and late design changes. The product turns the engineer's house information into a
cinematic presentation.
Desired outcome
A viewer should understand the house layout and feel the intended materials, lighting, atmosphere and movement
through the home. The film should feel like professional architectural visualization, while being represented
honestly as a generated visualization rather than footage of a real existing property.

 - The system does not claim to reproduce the real plot surroundings unless those surroundings are supplied or
 otherwise grounded.

Requirements and Acceptance Vocabulary
IMPLEMENTATION DESIGN
Every requirement should be expressed in a way a developer and reviewer can test, rather than as a
vague aspiration such as “perfect realism.”
Requirement types
Functional requirements describe actions the product must perform. Non-functional requirements describe latency,
reliability, privacy, cost and usability. Provider constraints describe what an external API can actually accept.
Acceptance test format
 - Given a valid house input, when Generate Video is selected, the system creates a job and displays its status.
 - Given a failed external generation, the job becomes recoverable or fails with a helpful explanation; it must not stay
 processing forever.
- Given a completed video, the user can play it, request changes, download it and access it later until its retention
 period expires.
Evidence rule
A requirement is complete only when code, automated tests or a repeatable manual test demonstrate it. A mockup
or an architecture diagram alone is not implementation evidence.
Detailed operating sequence
Start by preserving the original source and assigning it an artifact ID. Run deterministic checks before the AI step,
then pass only the validated artifact to the interpreter. Convert findings into a typed record with provenance, units
and field-level confidence. Downstream services consume the normalized record, not free-form prose. Keep the
original source available so a later parser or model upgrade can rebuild the derived representation without asking
the engineer to upload again.
Data contract and traceability
Each extracted fact should include its value, unit if applicable, source type, source location, confidence, criticality
and schema version. Explicit dimensions must remain distinguishable from inferred values. The API returns a safe
user-facing status while the job record stores the detailed parse report and any warnings. This makes a later
correction traceable to the exact input and interpretation version.
Failure and acceptance checks
 - Reject unsupported or corrupt input before any costly generation request.
 - Never silently convert a critical number, floor count or stair location when confidence is low.
 - Test clean files, scans, conflicting sources, missing elevations, malformed files and spoken technical terms.

Generate Video Action and Progress
IMPLEMENTATION DESIGN
The Generate Video control starts an asynchronous job; it should not hold the browser request open
until the video is finished.
When clicked
The frontend checks that at least one valid input is present, sends a create-job request, receives a job identifier
and navigates the same page into a progress state. Prevent accidental double submission using a disabled button
and idempotency key.
Progress model
Show the current stage and a truthful status. Do not invent a percentage if the vendor only reports
submitted/processing/succeeded/failed. A stage-based progress indicator is more honest than pretending each
stage has known duration.
Background operation
 - A worker processes the job and calls external services.
 - The frontend polls a status endpoint or listens to server-sent updates.
 - A browser refresh should reload the job state from the backend.
 
Detailed operating sequence
Treat each provider call as an asynchronous generation attempt with a persisted request, provider task ID, status
and cost record. Validate the returned clip before storing it. Assemble only clips that match the current model and
shot-plan versions. Run technical checks first, then visual continuity checks, then publish the final file. If a clip fails,
target that segment when dependencies allow; do not restart the whole job by default.
Version and correction semantics
A completed video is immutable. Every correction creates a child version pointing to its parent and records the
change type, impacted shots, updated prompt template, provider attempts, QA result and total cost. Presentation
changes preserve the model version; structural changes require a new model version and references. Retain the
last good version while a new one is being generated.
Failure and acceptance checks
 - Retries are bounded by attempt and cost budgets.
 - A provider failure or expired result URL must lead to a recoverable state, not a stuck spinner.
 - A video cannot be marked complete until the assembled file and minimum QA checks pass.

Review and Rectify Component
AGREED PRODUCT DECISION
Review & Rectify is a required product feature. The first generated video is shown for inspection, then
the engineer can request changes without composing a technical prompt.
Review screen
Show the video player, generation date, version, length and available actions. A Request Changes control opens
plain language: for example, “make the living room warmer” or “show the entrance more clearly.” The website
converts the instruction into a structured edit request.
Correction rules
Classify each request as presentation-only, scene-composition, camera/story or structural. Presentation requests
may change finishes or staging. Structural changes must modify the structured house requirements and
regenerate the model/reference package; do not pretend a prompt alone can safely change the locked model.
Acceptance
 - Keep prior versions.
 - Show which version is current.
 - Regenerate only affected clips when reliable dependency information exists; otherwise regenerate the affected
 sequence.
- Limit retries and expose an honest failure message if the request cannot be completed.

Download

03 / SYSTEM ARCHITECTURE
Provider Adapter Pattern
IMPLEMENTATION DESIGN
The website should be able to swap video-generation providers without redesigning the frontend or
rewriting the orchestration engine.
Canonical interface
Define capabilities such as supported input references, first/last frames, duration range, aspect ratios, resolution,
multi-shot mode, callback support, output URL expiry, audio option, commercial-use terms and cost unit.
Provider implementation
A provider adapter translates the canonical request to vendor-specific fields, invokes the API, maps vendor status
into internal status, retrieves output and normalizes errors.
Fallback policy
Use a fallback only when it supports the required reference/control pattern and the job can be safely reproduced. A
fallback must not silently switch to text-only generation if the hybrid's structural guidance is required.
Detailed operating sequence
Treat each provider call as an asynchronous generation attempt with a persisted request, provider task ID, status
and cost record. Validate the returned clip before storing it. Assemble only clips that match the current model and
shot-plan versions. Run technical checks first, then visual continuity checks, then publish the final file. If a clip fails,
target that segment when dependencies allow; do not restart the whole job by default.
Version and correction semantics
A completed video is immutable. Every correction creates a child version pointing to its parent and records the
change type, impacted shots, updated prompt template, provider attempts, QA result and total cost. Presentation
changes preserve the model version; structural changes require a new model version and references. Retain the
last good version while a new one is being generated.
Failure and acceptance checks
 - Retries are bounded by attempt and cost budgets.
 - A provider failure or expired result URL must lead to a recoverable state, not a stuck spinner.
 - A video cannot be marked complete until the assembled file and minimum QA checks pass.

Rate Limits and Idempotency
IMPLEMENTATION DESIGN
A single user can still accidentally double-click, refresh or trigger a retry that incurs duplicate provider
costs.
Rate limits
Limit job creation, upload throughput, active jobs and correction attempts. Set a monthly or daily spend ceiling.
Show a clear pause/failure when the budget is reached.
Idempotency
Generate a unique key for each intended submission. Persist it with the request hash and result job ID. If the same
key is repeated, return the existing job instead of charging again.
Retry accounting
Every provider attempt records expected cost, known actual cost, reason and parent attempt. Never hide retry
spend in a single blended line item.
Detailed operating sequence
The API validates identity and ownership, writes a durable job record and queues background work. Workers claim
jobs using leases or a queue acknowledgement, persist every important transition and communicate with external
systems through server-side credentials. Store structured metadata in the relational database and large files in
private object storage. Keep requests short and never run a full video generation inside the user-facing HTTP
request.
Boundary and data contract
Every boundary uses a typed request/response schema and a correlation ID. Persist provider task IDs, version IDs,
state transitions, error codes and timestamps. Do not put secrets or raw signed media URLs into normal logs.
Object access is private by default and ownership is checked on every project, file, job, video and share-link
request.
Failure and acceptance checks
 - Duplicate submissions return the existing job when the idempotency key matches.
 - Callbacks are authenticated or confirmed through a provider status query before success is trusted.
 - A user cannot read another project by changing an identifier in a URL.

Reliability and Recovery
IMPLEMENTATION DESIGN

Recovery design
